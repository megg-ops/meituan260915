## 1. 项目背景

### 当前实现基线（优先于下文历史讨论）

- 品牌已更名「周末拾光」；首页标题前与浏览器标签使用同一张水粉风阳光票根图标。图标由生图生成，页面引用 64px WebP，另有 32px PNG 备用。

- 2026-09-16 票根分享已实现：详情底部「查看地点」「分享票根」并列。浏览器原生 Canvas 使用现有插画和最近一次到访快照生成 900×1410 PNG，包含地点、日期、天气、伙伴（如有）和周末拾光署名；排除邮箱、消费金额和私人留言。支持预览、保存、生成失败重试；手机提示长按保存。不新增 AI 素材、不接后端、不生成公开票根链接、不调用系统社交分享。生成中关闭或切换面板不会把旧图片回填到新面板，预览退出后释放对象 URL。

- 2026-09-16 补充：默认游客进入，「我的」提供模拟登录与注册，注册可填写昵称。不连接服务器、不验证真实账号、不存储或发送密码；邮箱仅格式校验、测试密码至少 6 位。保存本机演示身份，退出保留票根和计划，不做账号隔离、云端同步或找回密码。登录页说明演示边界并提供游客继续入口。
- 全应用音乐入口采用音符，各页签均可直接点击播放、再次点击暂停，不弹出播放台。文字与背景区分播放状态，加载中再次点击取消，失败可重试。首次打开页面默认关闭，主动加载后全应用循环播放；切换页签或进入后台不由应用主动暂停。系统中断、网络失败和页面刷新不保证持续播放。

- 已实现四页签、3 个推荐、地点详情、周末计划、用户主动打卡、票根与收集；保留纯静态 HTML/CSS/JS，不新增依赖与后端。
- 杭州、北京、上海、广州、深圳均已接入手绘动画风城市探索插画、地图地点和伙伴位置。仅作艺术化示意，不用于测距或导航。
- 小雨最多 14 条短雨滴；小雪最多 12 颗圆润雪点。错峰、速度差、淡入淡出，限定地图区域。天气面板支持关闭动态并保存偏好；系统减少动态时隐藏雨雪粒子；页面后台暂停。
- 天气表达当前城市此刻的氛围，但数据仍为手动演示，不是真实天气或未来周末预报。未接天气接口与雨声。
- 一个可选、可命名的橘猫伙伴；基础姿态调整为面部朝前、身体轻微侧转、双前爪着地，避免背对扭头。庆祝姿态沿用。未做多品种或养成。
- 新票根保存城市地图图片路径和当次伙伴素材路径；旧票根兼容旧杭州取景与旧猫素材，不追溯改写记忆。
- 西湖有独立地点插画，其余地点暂用对应城市地图局部取景。高校认证、真实排行榜、真实地图定位、真实组队服务仍未实现。
- 验收重点：五城切换图片正确；选点不自动打卡；用户确认后出票；雨雪不遮挡点击与正文；关闭动态和刷新后偏好保持；旧记录可读。

下文保留产品规划与历史讨论；其中「待实现」「候选」描述若与本节冲突，以本节实际交付状态为准，未列入实现的候选不构成本轮承诺。

周末拾光是围绕「周末城市探索指南」题目设计的移动端产品雏形。当前版本通过城市、兴趣、预算、同行人数和模拟天气，为用户推荐本地活动，并提供组队、打卡和攻略能力。

现有版本已形成基本功能闭环，但仍存在三个主要问题：

1. 视觉风格较为模板化，大量渐变、圆角白卡片、胶囊标签和 Emoji 让产品缺乏独特审美与周末氛围。
2. 首屏功能较多但行动重点不明确，用户需要自行理解应该先筛选、浏览还是进入其他页签。
3. 打卡目前只是记录，没有形成值得回看、分享和持续收集的长期价值。

本轮改造目标不是继续堆叠功能，而是重新建立产品的第一印象、核心行动路径和留存机制。

## 2. 产品定位

### 2.1 一句话定位

帮助大学生发现适合自己的周末去处，并把每一次城市探索变成可以收藏的纪念。

### 2.2 核心价值

- 决策价值：减少在多个平台搜索、比较和纠结的时间。
- 情绪价值：让用户感受到周末临近的期待和出发的仪式感。
- 社交价值：通过同校身份和组队信息降低陌生人结伴门槛。
- 留存价值：通过地点票根与个人收藏册沉淀真实经历。

### 2.3 当前目标用户假设

已确认范围：面向多城市大学生的周末探索。杭州仅用于首轮视觉样例，不代表产品限制在杭州；样例优先表现学校周边、低预算、公共交通可达、半天或一天可往返的去处。现有五城不因样例选择而默认删减，完整插画地图的城市覆盖另行评估。

- 主要用户：18—25 岁、生活在高校或高校周边城市的大学生。
- 使用场景：工作日规划周末、周末临时寻找去处、活动结束后记录和分享。
- 典型问题：不知道去哪、信息太散、预算有限、找不到同行者、玩过之后没有沉淀。

> 待验证：大学生是否必须是唯一主用户，还是先作为产品切入人群，后续扩展至城市年轻人。

## 3. 产品体验目标

用户打开产品后，应在短时间内明确感受到：

1. 周末正在临近，值得期待。
2. 产品能够根据我的实际情况给出少量、明确的选择。
3. 我知道下一步应该点击哪里。
4. 完成一次探索后，我会获得一个值得保存的数字纪念品。

建议用以下核心体验链路约束后续设计：

```text
打开应用
→ 感受到周末临近
→ 表达这周想怎么玩
→ 获得 3 个明确推荐
→ 查看详情并安排出发
→ 组队或独自完成活动
→ 打卡并获得地点票根
→ 票根进入「我的收集」
→ 回看或分享，产生下一次探索动机
```

## 4. 产品设计原则

1. 先让人想出发，再让人设置条件：首屏优先建立周末情境，复杂筛选渐进出现。
2. 每个页面只有一个主要行动：其他能力根据用户所处阶段逐步出现。
3. 推荐必须少而明确：给出可解释的少量建议，而不是把筛选工作重新交给用户。
4. 经历比数据更值得收藏：打卡的结果应是一份独特纪念，而不只是一条统计记录。
5. 社交信息服务于信任：高校身份、校友数据和排行不能喧宾夺主或制造虚假可信度。
6. 演示数据必须诚实：Mock、模拟认证和种子数据需要明确标注，不伪装成真实在线数据。

## 5. 信息架构建议

### 5.1 一级导航

建议下一版探索以下结构：

| 页面 | 主要目的 | 核心内容 |
|---|---|---|
| 周末 | 找到这周末要做的事 | 周末倒计时、天气、个性化推荐、周末计划 |
| 组队 | 找到同行者 | 同校优先队伍、活动关联队伍、加入与发起 |
| 收集 | 查看已完成的探索 | 地点票根、城市收藏、解锁进度、回忆详情 |
| 我的 | 管理个人身份与偏好 | 高校身份、兴趣、预算、同行偏好、设置 |

原「攻略」不再默认占据一级页签，建议融入首页内容流和活动详情，作为决策辅助内容。

### 5.2 首页层级

首页建议按以下顺序组织：

1. 周末状态：倒计时、日期、城市与天气。
2. 唯一主行动：「帮我安排周末」或同类表达。
3. 渐进式偏好输入：兴趣、预算、同行人数。
4. 三个重点推荐：明确说明为什么适合用户。
5. 校园或城市中的轻量趋势信息。
6. 与推荐地点相关的攻略内容。

## 6. 功能需求

### 6.1 周末倒计时与情境首页（P0）

#### 用户价值

建立周末仪式感，并让首页每天具有轻微变化。

#### 表达规则

- 周一至周四：显示「距离周末还有 N 天」。
- 周五：显示「明天就是周末」。
- 周六、周日：显示「周末进行中」。
- 可结合城市和天气生成一句简短建议。

#### 验收标准

- 文案根据本地日期自动变化。
- 首屏无需滚动即可看到周末状态和主行动。
- 周末期间不会出现「距离下个周末还有 6 天」一类破坏情绪的机械表达。

### 6.2 个性化周末推荐（P0）

#### 输入

- 当前城市
- 兴趣类型
- 预算上限
- 同行方式或人数
- 天气状况

#### 输出

- 首轮突出展示不超过 3 个推荐。
- 每个推荐提供简洁且可解释的理由。
- 用户可以继续查看更多，而不是一开始面对完整活动库。

#### 交互原则

- 首页不直接铺开完整筛选面板。
- 推荐卡主动作统一为「查看安排」或「加入周末计划」。
- 组队、打卡等动作根据活动阶段在详情页中出现。

### 6.3 活动详情与出发安排（P0）

活动详情应至少包含：

- 地点或活动主视觉
- 时间、地点、费用和天气适配
- 推荐理由
- 相关攻略或注意事项
- 校友到访信息（有数据时）
- 加入周末计划或发起组队的主动作

打卡动作应在活动已经发生或用户主动进入完成流程时突出，避免与「组队」在活动发生前同级出现。

### 6.4 打卡票根（P0）

#### 用户故事

作为完成一次城市探索的用户，我希望获得一张具有地点特色的数字票根，以便保存这次经历并加入个人收藏。

#### 生成时机

用户主动确认到访后生成。地点与日期为必要字段，感想、天气、同行方式和花费可选。查看地图地点不构成打卡。

#### 票根内容

- 地点专属手绘漫画风插画
- 城市与地点名称
- 打卡日期与时间
- 当天天气
- 同行方式
- 用户的一句话心情或感想
- 收藏编号
- 地点专属印章
- 可选高校认证标记
- WeekendGO 品牌标识

#### 视觉要求

- 每个地点具有独立识别元素，例如西湖使用断桥、游船、远山或荷叶。
- 所有地点插画遵循统一的构图、线条、颜色数量和画幅比例。
- 插画本身不生成文字，票面文字由前端排版。
- 票根不能仅靠锯齿边框表达，应具备独立且值得收藏的主视觉。

#### 成功反馈

```text
打卡成功
→ 票根出现
→ 地点印章落下
→ 提示已收入「我的收集」
→ 查看收藏 / 生成分享图
```

反馈过程建议控制在约 1 秒，并兼容减少动态效果设置。

### 6.5 我的收集（P0/P1）

#### 主要能力

- 以票根为主要视觉展示已完成的探索。
- 支持按城市、时间或主题查看。
- 点击票根进入当次旅程详情。
- 未解锁地点可选择性显示为剪影，建立收集目标。
- 同一地点重复打卡时保留历史，但不机械重复发放完全相同的基础票根。

#### 可扩展机制

- 地点基础票根
- 春日、夜游、雨天等季节或条件限定版本
- 城市系列收藏进度
- 高校活动限定印章

### 6.6 组队（P1）

- 从活动详情发起关联队伍。
- 展示时间、集合点、缺少人数和发起者信息。
- 高校身份存在时，可提供同校优先信息。
- 当前 Demo 保留本地加入和退出能力。

> 待讨论：组队是否仍值得保留为一级页签，还是收敛到活动详情和「我的周末计划」。

### 6.7 高校身份（P1）

#### Demo 范围

- 用户选择学校。
- 展示「演示认证」或明确的 Demo 状态。
- 认证标记可出现在个人页、组队信息和票根上。

#### 正式产品所需能力

- 学校邮箱、学校合作或可信第三方认证。
- 认证失败和申诉流程。
- 学生证等敏感材料的存储、审核和删除策略。
- 在校生、毕业生等身份生命周期。

纯本地选择学校不得表达为真实认证。

### 6.8 校友足迹（P1）

优先在活动详情中展示轻量社交证明，例如：

- 「326 位本校校友来过」
- 「本周有 18 位同校同学收藏」

完整地图暂不作为首轮实现目标。真实地图需要地图 SDK、坐标数据、聚合展示、定位授权和隐私策略，投入较大。

### 6.9 高校探索榜（P2）

可以探索「本周高校探索榜」，但不建议长期按原始打卡总量直接排名。

潜在计分维度：

- 去重后的有效地点数
- 探索类型丰富度
- 每个地点的重复计数限制
- 周榜刷新
- 按学校规模归一化或分赛区

真实上线前必须考虑刷榜、虚假定位和学校规模差异。

## 7. 视觉与品牌方向

### 7.1 暂定视觉概念

用户已确认风格偏好：水彩、动画感、手绘。建议以柔和水彩色块、手绘轮廓和动画场景感表达地图、宠物与地点票根；文字、按钮与重要状态保持清晰。具体配色和质感浓度通过样板评审确定。「动画感」暂按造型与场景气质理解，实际动态效果单独设计和验证。

地图采用斜俯视的 2.5D 插画表现：通过山体侧面、湖岸厚度、遮挡、统一光向与投影表现高低，不要求真实 3D 建模，也不将艺术化高低表达为精确海拔。

「城市周末票根 / 周末行程册」

这是当前用于统一视觉语言的方向假设，还需要经过参考案例与原型验证。

### 7.2 视觉策略

- 用真实或统一风格的地点插画承担情绪表达。
- 保留暖色品牌锚点，但减少大面积橙黄渐变。
- 减少白色圆角卡片和胶囊标签的无差别使用。
- Emoji 只作为辅助情绪，不承担全部图标和主视觉职责。
- 使用统一图标语言、排版层级和交互状态。
- 通过日期、编号、地点、印章和路线形成可识别的票面语言。

### 7.3 插画资产原则

- 使用统一视觉模型和固定提示词模板生成或绘制。
- 固定画幅、透视、轮廓语言、色板和留白区域。
- 每个地点选择 2—4 个最具识别度的视觉元素。
- 避免直接生成文字，避免不同地点风格漂移。
- 首轮只为重点推荐地点制作少量高质量资产，不追求一次覆盖全部城市。

## 8. 数据与真实性说明

当前版本仍以 Mock 数据和 localStorage 为主。下一版必须区分：

- 真实数据：本地日期、用户主动输入的信息。
- 模拟数据：天气、活动供给、校友到访人数、排行榜。
- 演示状态：高校认证、组队成员、点赞数据。

在界面或产品说明中应以不干扰体验的方式说明数据属性，避免评审将演示能力误认为已经接入真实服务。

## 9. 非功能要求

- 移动端优先，重点验证约 360—430px 宽度。
- 兼容 iOS Safari 和常见安卓浏览器。
- 正文和重要操作满足基本颜色对比度要求。
- 所有交互具有清晰的点击、选中、禁用和成功状态。
- 动效支持 `prefers-reduced-motion`。
- 不因图片加载失败而导致关键信息不可用。
- 保持当前公开域名不变。

## 10. 技术与实现约束

### 10.1 当前框架判断

当前单文件 HTML、CSS、JavaScript 架构仍可支撑首轮视觉与流程验证。现阶段不建议仅为“显得工程化”迁移 React 或 Vue。

但若同时加入大量插画资产、分享图生成、复杂收藏状态和地图 SDK，单文件会迅速失去可维护性。建议按实施范围决定是否进行最小拆分。

### 10.2 建议的最小拆分

在不新增依赖的前提下，可考虑：

```text
index.html          页面骨架
styles.css          设计令牌、布局与组件样式
app.js              页面状态与初始化
data.js             城市、地点与种子数据
assets/tickets/     地点票根插画
```

是否拆分应在视觉原型和功能范围确定后决定，避免提前重构。

### 10.3 票根实现建议

- 地点插画使用静态位图资产。
- 票根结构使用 HTML/CSS，确保文字和动态字段清晰可控。

## 16. 新增候选：可定制宠物 / 出游伙伴

### 16.1 用户想法与解释假设

用户已明确：宠物是界面中陪伴用户旅游的虚拟伙伴。最低方案为固定一种小猫或小狗；时间允许时提供几种预设伙伴供选择和命名。若设计成本影响核心交付，可以取消。自由生成、换装和养成不属于本次已提出的必需范围。

### 16.2 与现有产品的连接

- 首页：陪伴用户等待周末，以简短动作回应天气或出发状态。
- 打卡：在出票时庆祝，也可作为票根边角的小印章，不遮挡地点插画。
- 收集：展示陪伴探索的记录，未来可通过探索解锁配饰。
- 我的：选择、命名或更换伙伴。跳过选择仍可使用全部核心功能。

价值假设：伙伴能增加亲近感和个人归属感。需要通过样板验证，不能直接假设它必然提高留存。

### 16.3 定制范围与成本

| 档位 | 范围 | 相对成本 | 主要工作 |
|---|---|---|---|
| 轻量伙伴 | 2—3 个预设角色、命名、一个基础姿态 | 中 | 角色风格统一、透明背景资产、选择入口与保存 |
| 组合定制 | 角色、毛色、少量配饰、有限动作 | 中高 | 分层资产、配饰锚点、遮挡关系和组合验证 |
| 自由生成 | 用户输入描述或照片生成任意宠物 | 高且不确定 | 生成服务、等待与失败流程、成本控制和结果一致性 |
| 养成系统 | 喂养、经验、任务、成长和解锁 | 高 | 持久状态、规则平衡、多阶段美术和交互 |

成本示例：3 种宠物 × 4 种天气 × 3 个动作，若逐张绘制就是 36 个状态资产；还未计入配饰。可复用基础姿态、独立配饰与天气图层减少资产数量，但仍需适配检查。

### 16.4 候选最小方案

先验证预设伙伴选择与命名，使用静态角色和一次轻量打卡反馈。不增加独立宠物页签。角色保存在本地，使用预制资产即可适配当前静态框架；无后端时不会跨设备同步。

暂不定优先级。建议先制作一种伙伴的站立与庆祝两个状态，验证和首页、地图、票根的适配，再决定是否增加第二种。用户关注陪伴出游，当前无需引入养成机制。

### 16.5 地图上的共同旅行（新增场景）

- 用户希望到达打卡点后，地图或地点界面展示自己与宠物在此游玩。
- 必须区分查看地点、加入计划和完成打卡；仅点击地图地点不能记录为已到达。
- Demo 可由用户主动确认到访后更新场景，并明确属于自报打卡；真实定位核验另行评估。
- 轻量候选：单城市探索示意图，展示少量地点及已打卡状态；人物和宠物作为独立图层出现在选中地点附近。示意图需标明不提供导航。
- 完整交互地图：拖动缩放、真实坐标、定位、路线等作为另一档范围，接入和验证成本更高。
- solo 出游时伙伴可以突出展示；多人出游时展示参与者或人数，宠物可选择保留为纪念元素。不同模式均不应强迫用户领养或丢失已命名伙伴。
- 不制作每个地点专属的人宠合照：先复用人物与宠物图层，地点特色由地图或票根插画承担。

## 17. 新增候选：天气驱动的界面与氛围

### 17.1 用户提出的四种状态

| 天气 | 场景 | 色彩方向 | 动态 / 声音候选 |
|---|---|---|---|
| 晴 | 太阳 | 暖黄色、橘色 | 克制的光照变化，默认无声 |
| 多云 | 云层 | 淡青色 | 缓慢云层移动，默认无声 |
| 雨 | 雨滴 | 蓝色 | 局部降雨、用户主动开启雨声 |
| 雪 | 雪花 | 偏白色 | 局部飘雪，深色文字保持可读性 |

以上是视觉方向，具体色值、动效强度和覆盖范围需经样板验证。

### 17.2 必须先明确的天气语义

- 当前天气：适用于此刻的城市氛围。
- 出行日天气：适用于周末计划与活动推荐，应标明日期。
- 模拟天气：用于演示四种状态，需标注「天气演示」。

已确认：首页主场景跟随当前城市此刻天气。周末推荐如使用出行日预报，必须单独标日期与来源，不能用当前天气假冒预报。尚未接入真实天气时标注天气演示。

### 17.3 建议落地结构

1. 语义层：统一晴、多云、雨、雪和未知状态，记录城市、对应日期及数据来源。
2. 主题层：用 CSS 变量切换场景背景、辅助色和装饰色，保留统一组件结构与品牌识别。
3. 场景层：天气插画和少量动画集中在首页顶部；阅读区保持稳定对比度。
4. 音效层：提供明确的声音开关，默认关闭；离开场景或页面隐藏时暂停，加载失败仍可正常使用。
5. 推荐层：当日出行可使用当前天气；未来出行使用对应日期预报。当前主题与出行日推荐天气分开保存并标明日期，雪天规则单独定义。

当前代码基础可支持主题变量、预制资产和有限的 CSS 动画，无须因四种天气单独迁移前端框架。雨雪粒子若需更复杂效果，再通过性能样例决定是否使用 Canvas；本轮未选库或接入服务。

### 17.4 分层成本评估

| 范围 | 相对成本 | 主要投入 |
|---|---|---|
| 四套配色 + 静态天气场景 | 中 | 四态美术、主题变量、文字和按钮对比度验证 |
| 局部云、雨、雪动画 | 中 | 动作调试、窄屏适配、低性能与减少动态效果降级 |
| 雨声开关 | 低至中 | 合适且可使用的音频、音量、播放和暂停状态 |
| 全页面随天气换肤 | 中高 | 各页组件与四套主题的状态组合验证 |
| 真实天气接入 | 单独估算 | 数据源、日期覆盖、凭据、失败回退与缓存方案 |
| 每地点 × 每天气独立插画 | 高 | 资产数量乘法增长、风格统一和后续维护 |

这里是相对工作量判断，不是工时承诺。确定画风和样板后，才能估算剩余地点的生产时间。

### 17.5 与票根、宠物的结合边界

- 天气场景使用可复用图层，地点票根保留独立主视觉，避免为每个地点重绘四版。
- 票根保存打卡时的日期和天气快照，不能随今天的天气改变过去的回忆。
- 已收藏票根若显示宠物，建议保存当次伙伴外观，后续换宠物不会改变旧票根。
- 宠物初期共享基础姿态，天气通过环境和少量配件表达。
- 雨雪不得遮挡操作或拦截点击；减少动态效果时提供静态场景，持续动画应能关闭。
- 没有天气数据时使用中性场景和「天气暂不可用」，不默认伪装成晴天。
